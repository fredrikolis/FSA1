# charlie — specification

The highest-level, implementation-free contract for charlie: a **vocabulary** of defined entities and
a set of **invariants** — timeless, positively-stated constraints on what the architecture *is*. Each
invariant carries a **fitness function**: the objective check that proves it.

The specification is **authoritative over the implementation** (spec-first): the code conforms to it,
never the reverse. It is a **living document owned by the product-manager workspace**; an invariant is
added or retired here, and a change to the code may not contradict an established invariant.

Items are grouped by **subsystem** and named by a stable, subsystem-scoped id — `CORE`, `FS`, `GRID`,
`VAL`, `ENG`, `CLI`. An id names one item for good (grep it to find every reference); new items append
within their subsystem, and a retired id is never reused. Within each subsystem the **definitions**
come first, then the **invariants** that constrain them.

## CORE — foundations (cross-cutting)

- **CORE1 · A1 addressing.** Every cell is addressed by the Excel A1 convention — column-letter/row-number coordinates, absolute markers, and inclusive range notation. — *`A1`, `$C$7`, and `F2:F11` parse and resolve to the coordinate set the A1 grammar defines, graded cell-for-cell against Excel's own resolution (ENG6).*
- **CORE2 · totality.** Every input yields a value or a located refusal. — *a malformed file or formula yields a diagnostic pointing at the offending location; no input produces a crash or a silent wrong value.*
- **CORE3 · the filesystem is the write surface.** The filesystem is the sole write surface for a workbook's authoritative content: an authoritative cell, tab, or file changes only when an author writes files directly. charlie-cli's writes to an existing workbook are confined to derived, non-authoritative data (`.cache/`, FS3); it may additionally materialize a new workbook — derived wholly from a source or a fixed template — into a location that is not already a workbook. — *a conformance/CLI test asserts that every charlie-cli command over an existing workbook leaves its authoritative cells, tabs, and files byte-identical and writes bytes only under `.cache/`; that no command accepts author-supplied cell content to write anywhere; and that a materializing command (`import`, `sample`) produces a workbook determined solely by its source or template — never by cell values passed on the command line — into a fresh, not-already-a-workbook location. An agent authors and repairs by writing files itself, guided by `--guide` and `check`.*

## FS — on-disk layout

- **FS1 · workbook / tab / file.** A workbook is a folder of tabs; a tab is a folder of files. — *each sub-folder of the workbook is a tab, except the reserved `.cache/` (FS3); the root and each tab may also hold name entries (FS4); a cross-tab reference is `Tab!A1`.*
- **FS2 · closed range.** A cell/grid file's name is a closed range — a bounded rectangle of A1 cells with inclusive endpoints; a **name** (FS4) is the exception, identified by an identifier rather than an A1 range. — *the file for rows 2–11 of column F is `F2:F11`; one cell is `A1`; a 3-wide by 8-tall block is `B2:D9`.*
- **FS3 · reserved derived-data directory.** A workbook segregates its derived data: one reserved location holds only regenerable, non-authoritative content, and no cell's value derives from it. — *discarding the reserved directory (`.cache/`, at the workbook root) changes no cell's value (VAL2), only the work to recompute one; a conformance test asserts a run with it deleted yields values identical to a run with it present (ENG4); the loader admits it as derived, not as a tab (FS1).*
- **FS4 · name.** A name is a filesystem entry — in a tab folder (sheet-scoped) or the workbook root (workbook-scoped) — identified by an identifier and resolving to a target cell, range, or value; it occupies no A1 coordinate (it is addressed by its identifier, not by position). — *a formula referencing a name evaluates against the name's resolved target; scope is location — a sheet-scoped name shadows a workbook-scoped one of the same identifier; names may overlap each other and cells freely (a cell may belong to any number of names); charlie refuses a name that parses as an A1 address (CORE2), so a name never collides with a cell's filename; a name that resolves to no cell, range, or value is a located `#NAME?` value (VAL3). The engine consumes only the resolved A1/value — it is A1/address-based (ENG1, CORE1); the on-disk representation of a name is a deserializer concern (GRID3), normalized to the same name at load.*

## GRID — deserialization (content → grid)

- **GRID1 · grid.** A cell/grid file's content is exactly its grid: for every coordinate in its closed range, one cell — an explicit value or an explicit `=formula` (unless the whole file is a single array formula that fills the range, GRID5). A name (FS4) is not a grid file. — *the grid of `F2:F11` is exactly ten cells, each a value or a formula; the file holds those cells and carries no header, annotation, or metadata.*
- **GRID2 · deserializer / generator.** A deserializer turns a file's content into its grid. A generator is a deserializer that computes the grid from a compact form rather than reading it cell-for-cell. — *a deserializer takes file content in some format and produces a grid; a generator's grid is the same artifact a file would otherwise list by hand.*
- **GRID3 · content → grid is engine-independent.** The engine operates only on a file's grid, never on the format the file is written in; the grid a file yields is independent of that format. — *`render --functions` shows the same grid whether a file is written by hand or produced by a generator (GRID2); a differential test that re-expresses one file in a different format yields a byte-identical grid and identical evaluated values.*
- **GRID4 · the grid fills its range.** A grid fills its file's closed range exactly. — *a `B2:D9` file whose grid is not 3×8 is a located dimension error.*
- **GRID5 · array formula fills its range.** A file's whole content may be a single `=formula` whose value is an array; that array fills the file's closed range exactly, one element per coordinate — the closed range is the author's explicit, bounded region an array occupies, and this is the only form in which one formula spans more than one cell. — *a `C1:C3` file whose sole content is `=SORT(A1:A3)` is the sorted 3×1 array in C1:C3; element `(r,c)` of the array fills coordinate `(r,c)`; a sole formula whose value is not an array of exactly the range's shape and orientation — a scalar, or a wrong-shaped array — is a located dimension error (GRID4), detected at evaluation; a one-cell file holding an array formula keeps only the array's top-left element; importing a spilled array over a region yields exactly the range file for that region.*
- **GRID6 · error locality.** A cell whose content cannot be deserialized is a located error value (VAL3) in the grid; every unrelated cell in the same file still loads and evaluates to its own value. — *an unparseable formula in one cell deserializes to a located error value (one of the six value types, VAL3) carrying its location, so it renders as that error and `charlie-cli check` reports it with a non-zero exit and its location while every other cell still yields its value (CORE2); this load-time error value is graded outside the ENG6 parity corpus (cf. GRID5); a grid that does not fill its range (GRID4), a malformed filename (FS2), or overlapping cell/grid files remain file-level refusals (CORE2), not cell error values.*

## VAL — the cell & value model

- **VAL1 · content, not position.** A cell's value derives only from its own content. — *placing identical content at any position yields the same value; two cells with different values necessarily differ in content (an array region is one array-formula cell spanning its range, not many cells sharing a formula, GRID5).*
- **VAL2 · no value from thin air.** Every value is a literal or a formula over other cells. — *every dependency chain bottoms out in written literals.*
- **VAL3 · the value model.** Every cell's value is one of {number, text, boolean, error, blank, array}. — *the type of every value is one of the six; no value carries a unit, label, or metadata field.*

## ENG — the engine (evaluation)

- **ENG1 · engine.** The engine is the evaluator: it computes each cell's value from the grids and the values of the cells that value references. — *the engine yields a value for every cell from grids alone, consuming no storage, format, or presentation input (independence is ENG5).*
- **ENG2 · evaluation.** A render computes only the cells its demand reaches, computes each such cell at most once, and yields a located `#REF!` for every reference cycle. — *rendering a viewport computes exactly the visible cells' dependency cone and no cell outside it; no cell is computed twice within a render; a reference cycle evaluates to a located `#REF!` (CORE2).*
- **ENG3 · optimization transparency.** Whatever optimization the engine applies, the value it computes for every cell equals a naive per-cell evaluation, and no optimization structure it uses is observable outside the engine. — *a differential test evaluates complex dependency chains both as a naive per-cell evaluation and through the engine and asserts identical values — including when references are first resolved to their effective form (a name FS4, or a reference-forging `INDIRECT`/`OFFSET` call ENG6 resolved to static references), where the naive oracle applies the same resolution — and a public-surface check confirms no engine-internal optimization type appears in any other module's interface.*
- **ENG4 · reuse is sound.** A cell's value is a deterministic function of its own content and its dependencies' values (VAL1, VAL2); any result the engine reuses — within a run or persisted across runs — instead of recomputing equals the value a fresh computation yields, and a cell always reflects the current content of itself and everything upstream, never a value that depends on unfolded runtime state (volatile references, clock reads). — *recomputing an unchanged cell reproduces its value; editing a cell changes exactly the values of it and its dependents and nothing else; a result reused — in memory, or from persisted derived data in `.cache/` (FS3) — is identical to one computed from scratch, and deleting all persisted derived data and re-running yields identical values (VAL2); a cell whose own or upstream content changed, and a cell whose value depends on runtime state (a reference-forging `INDIRECT`/`OFFSET` call, or a clock read `TODAY`/`NOW`), recompute rather than reuse — never served a stale result.*
- **ENG5 · engine independence.** The engine is independent of storage and presentation. — *the engine runs against an in-memory resolver with no filesystem present; storage or rendering can be replaced without changing it.*
- **ENG6 · Excel-compatible evaluation.** Every formula charlie evaluates yields the value a mainstream spreadsheet (Excel) yields — across functions, array semantics, reference resolution, and the value model. — *a differential conformance corpus grades charlie cell-for-cell against Excel's own outputs as the reference oracle; a divergence on any covered case is a defect. The corpus is the covered surface: parity holds over exactly the cases it covers, and cases where charlie deliberately diverges (e.g. a reference cycle as a located `#REF!`, ENG2; no dynamic spill, so a single-cell array formula keeps only its top-left element, GRID5; a reference-forging call — `INDIRECT`/`OFFSET` — whose own arguments forge, i.e. nested forging, is a located `#REF!`/`#NAME?` refusal, while a forging call with non-forging arguments is supported and graded in the corpus) fall outside it.*
- **ENG7 · retired.** Folded into ENG4 — persistent-cache reuse is the same soundness need as in-memory reuse, and ENG4's fitness function now carries the persistent-and-volatility clauses. This id is retired and never reused.

## CLI — the tool

- **CLI1 · self-contained tool.** The tool is charlie-cli, a command-line program; everything an agent needs to author, render, validate, and repair a workbook is obtainable from charlie-cli alone. — *`charlie-cli --guide` states the format's rules, `charlie-cli sample` writes a workbook that loads and renders, and `charlie-cli check` validates one and locates every fault; every refusal carries its location (CORE2); an agent given only charlie-cli — no companion document, repository, or service — can author a valid workbook by writing its files per `--guide` (the filesystem is the write surface, CORE3) and repair a rejected one from `check`'s located diagnostics.*
- **CLI2 · trace (dependency inspection).** charlie-cli reports a cell's upstream dependencies and downstream consumers. — *`charlie-cli trace <cell>` lists the cells it reads (transitively) and `--dependents` lists the cells that read it (transitively); the reported edges are exactly the engine's own dependency relation (ENG3) — dependents are that relation transposed, not a separately derived parse; it is cycle-safe (a cycle is reported, not looped, ENG2); each node carries its value; the engine's internal dependency-graph type never appears in the output (ENG3 containment).*
- **CLI3 · tree (workbook structure).** charlie-cli renders a workbook's complete structure — every tab, cell, and name — as a single read-only view. — *`charlie-cli tree` presents every authored entry on disk: each tab (FS1), each cell of every cell/range file (FS2, GRID1), and each name (FS4), each shown with its content — and never the derived, non-authoritative `.cache/` (FS3). A conformance/CLI test asserts that `tree` presents exactly the authored cells and names on disk and no derived data, and leaves the workbook byte-identical (CORE3).*
